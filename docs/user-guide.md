3. อ่านคำอธิบายและคำถามซักต่อทางขวา

# โหมดผู้เชี่ยวชาญ

เลือก **ผู้เชี่ยวชาญ** ที่แถบโหมดผู้ใช้ แล้วเลือกบริเวณบนร่างกาย หรือค้นคลังความรู้ แบบฟอร์มตรวจอยู่ใต้ข้อมูลบริเวณและใต้แต่ละบทความ (ไม่ครอบคลุมข้อความจาก private vault)

ระบุชื่อ สาขา/คุณวุฒิ/หน่วยงาน และเหตุผลประกอบ เลือกผล **ตรวจแล้ว**, **ต้องแก้ไข** หรือ **รับรองเนื้อหาฉบับนี้** หากเลือกต้องแก้ไข ให้ระบุข้อความที่ผิดและข้อเสนอแก้ไขด้วย บันทึกแต่ละครั้งจะเพิ่มประวัติ พร้อมวันที่และสำเนาเนื้อหาที่ตรวจ หากเนื้อหาเปลี่ยน ผลเดิมจะไม่ถือเป็นผลตรวจของฉบับใหม่

ผลตรวจและความเห็นอ่านได้ในทุกโหมดที่แสดงเนื้อหานั้น เลือก **ส่งออกผลตรวจทั้งหมด (JSON)** เพื่อส่งไฟล์ให้ผู้ดูแลนำไปแก้เนื้อหา ผลตรวจไม่แก้บทความต้นฉบับหรือสถานะเผยแพร่โดยอัตโนมัติ

ปุ่ม **บันทึกผลตรวจ** ยังเก็บเฉพาะใน localStorage และไม่ได้ยืนยันตัวตน การล้างข้อมูลเว็บไซต์จะลบประวัติในเครื่อง จึงควรส่งออกเก็บไว้ ส่วน **ส่งข้อเสนอถึงผู้พัฒนา** ใช้ระบบบัญชีและคิวกลางด้านล่าง

## ส่งข้อเสนอถึงผู้พัฒนาและตรวจซ้ำ

### ทดลองบน GitHub Pages

หน้าเว็บสาธารณะมีเดโมแบบ static สำหรับทดลอง workflow โดยไม่ต้องมีบัญชี:

- เปิดแผนที่แล้วเลือก **ผู้เชี่ยวชาญ** เพื่อเขียนความเห็นและส่งเข้าคิวเดโม
- เปิด **เดโมผู้เชี่ยวชาญ · คิวตรวจเนื้อหา** เพื่อสลับบทบาทผู้เชี่ยวชาญ/ผู้พัฒนา
- ทดลองรับงาน แก้ข้อความจำลอง ส่งตรวจซ้ำ ขอแก้เพิ่มเติม และรับรองปิดงานได้ครบวงจร

ข้อมูลเดโมเก็บใน localStorage ของเบราว์เซอร์นั้นเท่านั้น ไม่ส่งถึงผู้พัฒนาจริง ไม่แก้ไฟล์ต้นฉบับ และไม่ถือเป็นการรับรองจริง หน้าเดโมแสดงข้อความนี้ตลอดการทดลอง

1. เปิด **เข้าสู่ระบบ / คิวตรวจเนื้อหา** แล้วเข้าสู่ระบบด้วยบัญชีผู้เชี่ยวชาญที่ผู้ดูแลจัดให้
2. กลับแผนที่ เลือกโหมดผู้เชี่ยวชาญ เขียนความเห็นใต้เนื้อหา แล้วกด **ส่งข้อเสนอถึงผู้พัฒนา** เมื่อสำเร็จจะมีหมายเลขงาน ชื่อผู้ส่งอ้างจากบัญชี ไม่ใช่ชื่อที่กรอกในแบบฟอร์มท้องถิ่น
3. ผู้พัฒนาเข้าสู่หน้า `/web/reviews.html` ด้วยบัญชีผู้พัฒนา จะเห็นข้อเสนอทั้งหมด เลือก **เริ่มแก้ไข** พร้อมคำตอบ
4. ผู้พัฒนาแก้ไฟล์เนื้อหาจริง (`knowledge/*.md` แล้วรัน `python scripts/build-knowledge.py` หรือแก้ข้อมูลโซน) จากนั้นรีเฟรชคิวและเลือก **ส่งให้ตรวจซ้ำ** ระบบเก็บฉบับปัจจุบันไว้ในประวัติ
5. ผู้เชี่ยวชาญเจ้าของข้อเสนอเปิดเนื้อหาฉบับที่ส่งตรวจและฉบับปัจจุบัน แล้วเลือก **รับรองและปิดงาน** หรือ **ขอแก้ไขเพิ่มเติม** พร้อมเหตุผล ผู้พัฒนาปิดงานแทนผู้เชี่ยวชาญไม่ได้

สถานะ: ส่งแล้ว → กำลังแก้ไข → รอตรวจซ้ำ → ปิดแล้ว หากขอแก้เพิ่มเติมจะกลับไปกำลังแก้ไข ทุกคำตอบเก็บชื่อบัญชี เวลา และสำเนาเนื้อหา หากฉบับปัจจุบันเปลี่ยนระหว่างรอตรวจ ต้องส่งตรวจใหม่ก่อนรับรอง

ผู้เชี่ยวชาญเห็นข้อเสนอของตัวเอง ผู้พัฒนาเห็นทั้งหมด กดรีเฟรชคิวเพื่อติดตามคำตอบ ยังไม่มีอีเมลแจ้งเตือน และการปิดงานไม่แก้ `review_status` ในบทความต้นฉบับอัตโนมัติ ผลรับรองในคิวอ้างเฉพาะฉบับที่ตรวจ ไม่ใช่การยืนยันคุณวุฒิจากหน่วยงานภายนอก

## เตรียมบัญชีและเซิร์ฟเวอร์สำหรับผู้ดูแล

ผู้ดูแลตรวจสอบชื่อและคุณวุฒิก่อนสร้างบัญชี รันจากโฟลเดอร์โครงการ (ชื่อด้านล่างเป็นตัวอย่าง):

```powershell
python scripts/review_store.py developer --name "ผู้พัฒนา" --role developer
python scripts/review_store.py expert --name "ผู้เชี่ยวชาญ" --role expert
python scripts/serve-web.py
```

คำสั่งจะถามรหัสผ่านและให้ยืนยันโดยไม่แสดงบนจอ อย่างน้อย 12 ตัวอักษร ไม่ต้องใส่รหัสผ่านในคำสั่งหรือส่งในแชต ใช้ชื่อบัญชีเดิมเพื่อเปลี่ยนรหัสผ่าน/สิทธิ์ได้ เซสชันเดิมจะถูกยกเลิก ไม่มีบัญชีหรือรหัสผ่านเริ่มต้น

SQLite อยู่ใน `.review-data/reviews.sqlite3` ซึ่งไม่อยู่ใน Git และไม่เปิดให้ดาวน์โหลดผ่านเว็บ สำรองไฟล์นี้เมื่อหยุดเซิร์ฟเวอร์ หากต้องการเปลี่ยนที่เก็บ ตั้ง `BODY_PAIN_REVIEW_DB` ให้ชี้ไปนอก `web/` และ `data/` ก่อนรันทั้งคำสั่งบัญชีและเซิร์ฟเวอร์

URL `127.0.0.1` ใช้งานได้เฉพาะเครื่องที่เปิดเซิร์ฟเวอร์ การทำงานข้ามเครื่องต้องใช้เซิร์ฟเวอร์เดียวกันผ่าน HTTPS reverse proxy ที่ผู้ดูแลจัดเตรียม ตั้ง `BODY_PAIN_PUBLIC_ORIGIN` เป็น origin จริง เช่น `https://review.example.org` (ไม่มี slash ท้าย) และจำกัดอัตราการเข้าสู่ระบบที่ proxy แอปยัง bind เฉพาะ loopback และไม่ได้เปิดสู่ภายนอกอัตโนมัติ

เมื่อออฟไลน์ยังอ่านแผนที่และบันทึกผลตรวจในเครื่องได้ แต่ส่งข้อเสนอหรืออ่านคิวกลางไม่ได้ ข้อความที่ยังส่งไม่สำเร็จคงอยู่ในฟอร์มจนเปลี่ยนหน้าหรือโหลดใหม่ ให้บันทึกในเครื่องหรือคัดลอกก่อนออกจากหน้า
